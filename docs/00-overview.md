# 00 · 愿景与设计原则

## 目标

**不是「记录打卡」，而是「帮大家更早睡」。** 打卡只是记录睡眠时间的工具。

早睡难坚持，本质是回报结构不利：代价（放下手机、退出娱乐）是即时的，回报（第二天精神好）是延迟且弥散的。所以一切机制围绕一句话：

> 把「即时代价」改造成「即时奖励」，把「延迟回报」变得具体、可见、可期待。

## 三条核心规则（不可违背）

| 情境 | 待遇 |
|---|---|
| 早睡（打卡 ≤ 个人目标时间） | 即时庆祝；计入早睡天数 |
| 晚睡（打卡 > 目标时间） | 即时温和提醒（不羞辱）；计入统计，体现在月报/年报 |
| 无记录（忘打卡/没打卡） | **无惩罚，不纳入早/晚统计** |

## 正反馈机制清单

1. **即时回执**：打卡 1 秒内得到有温度的回执（早睡=庆祝，晚睡=温和提醒 + 一句「明天提前一点点」）
2. **隐藏连续奖励**：连续早睡达标（7/21/30/66/100）才揭示惊喜奖牌。日常**只展示累计早睡天数与占比，绝不展示 streak**（见 §05）
3. **跟自己比**：进步指标 = 与自己上周平均就寝时间比，不做绝对时间排名
4. **宽松的成功定义**：只要睡前打了卡就算记录（早/晚区分是统计维度，不是惩罚）
5. **群体目标**：可选的集体成就（如「本周全队 X 天早睡」）
6. **睡前思考题**：已打卡但睡不着时，可领一道闭眼可想的题助眠（无压力、无判题，睡着了=成功）

## 要避免的反模式

- 公开羞辱晚睡的人 → 退群
- 纯排行榜竞争 → 垫底者放弃
- 打卡流程复杂（>3 秒）→ 摩擦杀死习惯
- 惩罚/罚款 → 短期有效，长期反感
- 把「打卡」本身变成被考核的指标 → 催生「晚睡就不打卡」的作弊心态

## 技术选型（为什么）

| 选择 | 理由 |
|---|---|
| TypeScript + strict + 全类型 | 类型是多 agent 协作的接口契约，防止互相踩踏 |
| pnpm monorepo + TS project references | 模块独立成包、按依赖拓扑构建，agent 各管各的包 |
| SQLite（better-sqlite3） | 单文件零运维，2c2g VPS 最省心 |
| Hono + React/Vite + node-cron + ntfy | 轻量、生态成熟、ntfy 已部署 |
